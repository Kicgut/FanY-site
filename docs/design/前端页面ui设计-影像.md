# 前端页面 UI 设计：影像档案、相册与照片详情

## 1. 目标与范围

影像页是独立于“作品”的照片档案入口。它既要让访客按相册阅读有主题的影像叙事，也要让未收入相册的独立照片被发现、筛选和放大观看；不能把所有照片强行塞入相册，也不能把相册列表误做成照片瀑布流。

页面与首页、文章和作品保持深海军蓝、低饱和雾气、冰青强调色、细边框与深色毛玻璃语言。背景只保留轻微星点/雾感环境层，图片本身是唯一视觉主角：图片不套厚重彩色滤镜，容器不使用抢眼渐变或频繁动效。

本设计覆盖：

- `/albums`：影像档案总入口，包含“相册”和“全部影像（含未归册）”。
- `/albums/:id`：单个相册的阅读与筛选。
- `/photos/:id` 或查看器路由：单张照片的大图、关键信息、完整元数据和前后切换。

## 2. 当前实现与 UI 不足

当前公开相册列表位于 `nuxt-app/pages/albums/index.vue`，相册详情位于 `nuxt-app/pages/albums/[id].vue`。照片数据模型已具备拍摄时间、地点、相机、镜头、ISO、焦距、尺寸、关键词、标签和相册关联等基础，但这些能力没有完整地转化为公开浏览体验。

### 2.1 影像入口不足

- 当前 `/albums` 只有相册卡片，公开且未被收录进任何相册的照片没有单独入口，访客无法发现它们。
- 页面仍使用浅色背景、白色卡片，和已确定的深色电影感公开站不一致。
- 相册搜索只覆盖名称和描述，排序仅有“最新 / 最多照片 / 名称”；不支持年度、月份、主题标签、媒介/方向、地点和拍摄时间筛选。
- 预览马赛克缺乏尺寸和信息层级规范；相册封面、张数、日期和主题之间的边界不够明确。
- 上传入口混在公开浏览页。登录后的管理/上传能力应被收入工具区或后台，而不是成为影像档案主视觉的一部分。

### 2.2 相册内浏览不足

- 相册详情只支持文字搜索和单标签筛选；筛选状态不映射到 URL，也没有日期、地点、相机或多标签组合。
- 图片缩略图的标题与标签只在覆盖层出现，关键信息不能稳定阅读；但若始终展开，又会破坏照片的纯粹性。
- 相册详情接口当前未把 `takenAt`、`location`、`cameraMake`、`cameraModel`、`lens`、`iso`、`focalLength` 等字段选择并返回给页面，导致前端已有格式化函数也拿不到实际 EXIF 信息。
- 加载更多使用页码，但筛选仅在已加载照片中执行，长相册会产生“筛选结果不完整”的误解。

### 2.3 大图查看不足

- 现有灯箱已有左右键、关闭、中图优先与按需原图加载，基础方向正确；但信息只堆在图片下方，缺少稳定的“照片舞台 + 可折叠信息侧栏”结构。
- 无缩略图胶片带、当前序号、相册归属、标签、可用下载状态和清晰的全屏/信息切换，长相册中定位较弱。
- 未定义触屏手势、焦点管理、滚动锁定、图片比例适配、元数据缺失和原图权限被拒绝时的行为。

## 3. 研究结论与设计原则

成熟照片产品将“按相册组织”与“按所有照片发现”并列，而非二选一；相册可以有封面、数量和排序，照片库则通过时间、关键词和元数据缩小范围。[Google Photos 的相册筛选与排序说明](https://support.google.com/photos/answer/6128849?co=GENIE.Platform%3DAndroid&hl=en) 与 [Adobe Lightroom 的照片组织、筛选和信息面板](https://helpx.adobe.com/lightroom/desktop/organize-photos/organize-photos.html) 都体现了这一点。Lightroom 也将相机、镜头、地点、ISO 等设为可选筛选维度，并在单图信息面板中按需展示元数据，而不是压满缩略图。[官方筛选说明](https://helpx.adobe.com/lightroom/mobile/search-and-filter-photos/filter-photos-and-videos.html)

由此确立以下原则：

1. **双入口而非双份数据**：相册是主题集合；“全部影像”是同一照片资源池的发现视图，能显示“未归册”筛选，但不复制照片。
2. **缩略图保持安静，信息按需出现**：网格默认只保留极短的日期/标题提示；悬停、键盘聚焦或触摸后才展示标签与查看动作。
3. **筛选分层**：常用的时间、相册、标签放在可见筛选条；相机、镜头、焦距、ISO、方向、地点收纳进“更多筛选”抽屉，避免工具栏失控。
4. **照片优先于容器**：相册卡片使用毛玻璃信息层，照片网格使用极细边框和低透明暗底，不给每张照片套明显玻璃卡。
5. **单图是沉浸式舞台**：大图始终优先，信息可切换、可访问、可折叠；用户不应离开图片才能了解其拍摄信息。
6. **公开边界不松动**：只展示通过审核且当前访客有权查看的照片和相册；原图、精确 GPS、私有相册归属及管理状态必须按现有权限策略分别控制。

## 4. 影像档案总入口（`/albums`）

### 4.1 信息架构

入口页名称统一为“影像”，路由可保持 `/albums` 以兼容现有链接。桌面端结构：

```text
固定顶部悬浮导航
└── IMAGE ARCHIVE / 影像 / 简短说明 / 公开照片总数
    ├── 视图切换：相册 | 全部影像
    ├── 搜索、时间、标签和更多筛选
    ├── 相册视图：精选相册 + 相册网格
    └── 全部影像视图：未归册提示 + 照片网格 + 分页/加载更多
```

“相册”是默认视图；“全部影像”显示全部可见照片，并提供 `仅未归册` 开关。切换、搜索、筛选、排序、分页应同步 URL，例如：`/albums?view=photos&year=2026&month=07&tags=night,coast&unfiled=1&sort=takenAt-desc`。

### 4.2 标题区与视图切换

- 标题区显示 `IMAGE ARCHIVE`、主标题“影像”、一句克制说明以及“相册数 / 可浏览照片数”；不要使用首页地球或小猫跨区动画。
- 使用等权的文字标签页“相册”“全部影像”，当前项仅以冰青细下划线和较亮文字标示，不使用重型胶囊。
- 右侧允许小型静态蔚蓝地球线框环境标记；若屏幕不足则隐藏，绝不覆盖图片。

### 4.3 筛选与排序

筛选值由后端执行，前端只显示当前页结果与准确总数。照片和相册的筛选能力不同，切换视图后只显示有意义的控件。

| 层级 | 照片筛选 | 相册筛选 |
| --- | --- | --- |
| 常用可见 | 搜索、年份、月份、标签、相册归属（全部/仅未归册）、排序 | 搜索、年份、主题标签、排序 |
| “更多筛选” | 地点、相机机身、镜头、ISO 区间、焦距区间、横/竖/方构图、文件类型 | 照片数量范围、创建/最近更新区间 |
| 排序 | 拍摄时间新旧、上传时间新旧、标题 | 最近更新、最近拍摄、照片数、名称 |

- 多标签采用 AND/OR 明确切换（默认 `AND`），筛选条显示可关闭 token 和“清除全部”。
- 年份选择后月份才可用；没有某年/月数据时不显示虚假选项。
- 搜索兼容标题、描述、标签、关键词与地点；不承诺未建立索引的 AI 语义检索。
- 结果区明确显示“找到 128 张”“仅未归册 24 张”等反馈；加载、空结果、失败、无更多结果都有稳定状态。

### 4.4 相册视图容器

- 顶部可有最多一个精选相册横幅：大封面 + 毛玻璃信息板（相册名、短描述、拍摄时间范围、张数、主题标签）。没有明确精选数据则不渲染该横幅。
- 常规相册使用 3 列网格，封面固定 `4:3`，可使用最多 4 张预览照片做克制拼贴；图片之间保留 2–4px 暗色缝隙。
- 卡片下半区是深色半透明信息带：相册标题、张数、时间范围与最多两个标签；“进入相册”只在悬停/聚焦或触摸激活时出现。
- 卡片是一个完整链接；内部不嵌套其他链接或按钮。

### 4.5 全部影像视图容器

- 使用响应式“规整拼贴网格”：保留原始横竖比例，以 4–6 列视觉节奏排列；不将所有图裁成相同方形。优先使用 CSS Grid/服务端已知宽高设置 `aspect-ratio` 防止布局跳动。
- 缩略图外仅保留 `1px` 低亮边框、`8px` 圆角和深色底，不给每张图再包厚毛玻璃卡片。
- 鼠标悬停/键盘聚焦显示低透明渐层信息：标题或拍摄日期、相册归属（若有）、最多 2 个标签及“查看照片”。移动端改为点击打开，不强制覆盖层常驻。
- 未归册照片在信息层显示 `UNFILED / 未归册`，帮助理解其归属，而不暗示其不完整。

## 5. 相册阅读页（`/albums/:id`）

相册页服务于主题连续观看，首屏不应是巨大且压迫的 banner。采用“相册信息带 + 纯照片网格”的结构：

```text
返回影像 / 相册标题、说明、时间范围、张数、标签
筛选条（相册内搜索、时间、标签、更多）
照片拼贴网格
└── 点击任一张 → 照片查看器（保留筛选后的相册序列）
```

- 相册信息带为横向深色毛玻璃，展示标题、简介、照片数、筛选结果数和有限的主题标签；没有描述不保留空白大块。
- 保留相册自定义排序（`AlbumPhoto.order`）作为默认；用户改用“拍摄时间”后，URL 明确记录排序方式。
- 相册内部也支持多标签、年份/月度、地点和相机等筛选，但默认仅露出搜索、标签和时间，以避免干扰观看。
- 筛选必须由 API 返回完整结果再分页，不能只过滤客户端已经加载的 50 张。

## 6. 照片查看器与独立照片详情（`/photos/:id`）

### 6.1 查看器结构

点击网格图片后在客户端进入查看器状态；推荐同时写入可分享 URL（如 `/photos/812?from=album:22&index=8` 或 `?from=archive&filters=...`），刷新后可继续查看该照片。桌面端：

```text
暗色遮罩 / 关闭按钮 / 当前 08 of 42 / 上一张、下一张
├── 图片舞台（按比例完整显示，点击可放大）
└── 可折叠右侧信息栏
    ├── 标题、拍摄日期、描述、标签、相册归属
    ├── 关键 EXIF（相机、镜头、焦距、光圈/快门如未来有字段、ISO、尺寸）
    ├── 地点（公开时显示模糊地点；精确 GPS 仅有额外授权时显示）
    └── 操作：显示/隐藏信息、全屏、查看原图/下载（仅 allowOriginalDownload）
```

- 图片舞台以 `object-fit: contain` 保证完整照片，深色背景承接留白；不把宽高不一的图片拉伸、裁切或铺满。
- 信息栏默认在桌面打开、移动端收起；元数据按字段实际存在时显示，不能产生“镜头：—”一排排空信息。
- `查看原图` 不是默认加载，也不等于公开下载。只有服务端确认 `allowOriginalDownload` 才出现；无权限时不显示该操作，也不能猜测原图 URL。
- 键盘支持 `Esc` 关闭、左右箭头切换；打开后焦点进入查看器，关闭后回到原缩略图；背景滚动锁定。
- 下一张预加载中图即可；网络慢时显示非阻塞加载状态，原图失败可回退中图。

### 6.2 数据与元数据补齐

`Photo` 模型已有大部分展示所需字段，但目前公开相册详情查询只取了 URL、尺寸和标签。实现本设计时必须让权限校验后的 `presentPhoto()` 输出与页面需求一致：

- 列表：`id`、标题、缩略图/中图、`width`、`height`、`takenAt`、标签、公开可见的相册摘要、可选地点。
- 单图：增加相机、镜头、ISO、焦距、关键词、文件大小与 mime 类型；EXIF 仅在有值时展示。
- 如需展示光圈、快门、曝光补偿等，必须新增显式 Prisma 字段、migration、导入链路和回滚说明，不能从字符串描述中猜测。
- 年/月、标签、未归册、地点、相机和方向筛选需要服务端参数验证、白名单排序字段、正确索引与准确 `total`；不要从客户端全量下载照片做筛选。

## 7. 移动端设计

在 `max-width: 760px`：

- 顶部导航使用现有全屏/半屏抽屉；“相册 / 全部影像”保持可见的水平标签页。
- 影像网格为 2 列规整拼贴，保留比例，图片间距 6–8px；相册卡片为单列或横向滑动精选 + 单列列表。
- 搜索常驻，年份、标签与更多筛选进入底部抽屉；应用和清除筛选按钮固定在抽屉底部，触控目标至少 44px。
- 查看器全屏显示图片，底部显示“当前张 / 总数”和上一张/下一张大触控区；信息栏从底部上拉半屏展开，默认只显示标题、日期、相册归属和“更多信息”。
- 不依赖悬停；所有原本 hover 才出现的信息和操作都通过点击后查看器获得。双指缩放交由浏览器/图片手势处理，页面不抢夺基本触摸行为。
- 当 `prefers-reduced-motion` 时关闭查看器淡入、网格缩放和图片过渡，仅保留即时状态变化。

## 8. 可访问性、性能与验收

- 网格使用语义化列表；每张可查看照片使用明确按钮/链接名称，例如“查看照片：夜航，2026 年 7 月 12 日”，不能只依赖图片文件名。
- 所有缩略图有准确 alt；纯装饰拼贴图使用空 alt，避免相册名称被连续读出多次。
- 按钮、筛选 token、查看器关闭与前后切换可键盘操作，焦点样式清晰；查看器满足焦点陷阱和 `aria-modal` 语义。
- 首屏仅加载必要缩略图；其余图片 `loading="lazy"`、`decoding="async"`，提供宽高/`aspect-ratio`。大图和原图按点击加载，预加载仅限相邻一张中图。
- 所有筛选与分页状态写入 URL；空、加载、失败、无更多结果均提供文字反馈。
- 验收至少覆盖：相册与未归册照片都可被发现；组合筛选结果准确；横/竖图无布局跳动；查看器不裁切图片且可键盘/触摸切换；只在允许时看到原图；移动端页面无横向溢出；非公开照片、精确 GPS 和管理元数据不泄露。
